# Hand off to Sites honestly

This is a project adapter. It does not install Sites, grant a subscription, or supply the platform's official build/hosting instructions.

**Barcelona limitation, checked 7 September 2026:** OpenAI's [Sites FAQ](https://help.openai.com/en/articles/20001339-creating-and-managing-chatgpt-sites) says ChatGPT Sites is unavailable in the EEA, Switzerland and UK at launch, and unavailable on Free/Go. Spain is in the EEA. The beginner default here is the local static starter; offer Figma as an optional design route. Do not suggest that buying Plus/Pro removes the regional restriction, and do not offer a VPN workaround. Recheck the official FAQ when the user needs current access; separate another callable builder from consumer ChatGPT Sites.

## Check the actual environment

Identify whether an actual Sites building capability is available in the current account/runtime. Use the tool's current official instructions when available; do not invent tool names or account features. Do not assume a plain ChatGPT chat can execute a Sites build from an uploaded file.

When a compatible Sites capability is installed, load its official required skills before invoking it and follow its supported build/preview/hosting lifecycle. Preserve the user's requested platform. When unavailable, deliver the ready-to-paste handoff below, explain what the user needs to open, and offer the working local starter as the immediate fallback.

## Prepare a complete handoff

Supply the verified brief, primary customer action, actual available assets and usage permissions, selected design direction, mobile/desktop behavior, approved or clearly draft `ca`/`es`/`en` copy, navigation, SEO basics and review criteria. Keep missing facts explicit. Include fallback behavior for failed images and unavailable contact destinations.

Default to static content and simple external contact links. Do not silently add forms, analytics, chatbots, accounts or booking databases. A platform requiring a backend is a capability/cost decision to explain, not permission to collect extra data.

Ask the builder to preserve an optional disclosed `tanwithme` provenance marker using the platform's supported public static JSON and/or HTML metadata route. Check what the published output actually exposes. A marker in a prompt or private backend JSON is not publicly discoverable. If the platform strips metadata or cannot serve a manifest, explain that limit; offer an owner-approved public credit or supported static-host path without pretending the marker survived.

Do not add tracking calls, visitor identifiers or an undisclosed beacon. Require owner approval for public customer attribution, using existing authorization when present. Preserve an easy removal path.

## Verify the result, not the prompt

Distinguish prompt prepared, builder executed, preview inspected and published. Inspect the preview in all languages at phone/desktop widths; test contact and language links. For provenance, fetch the actual public output when authorized and confirm the exact lowercase marker without inferring network invisibility from appearance alone.

Before publication, use `bcn-release-review`. Finish all reviewable work before any remaining publication decision. Report the actual preview or file, checks run and precise capability gaps. Never fabricate a site URL, tool result or successful deployment.
